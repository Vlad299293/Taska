## 1. Обзор

Цель — внедрить систематический подход к обработке всех возможных сбоев в приложении Taska, чтобы пользователь всегда получал понятный, человекочитаемый ответ вместо технических логов или "молчаливого" отказа системы.

**Scope**
- **Инфраструктура ошибок**: Создание иерархии классов ошибок и сервиса маппинга.
- **Слой API**: Обертывание вызовов Supabase для перехвата сетевых и авторизационных ошибок.
- **Слой UI**: Внедрение системы уведомлений (Toasts) и глобальных границ ошибок (Error Boundaries).
- **Синхронизация**: Обработка состояний Offline/Online и конфликтов данных.

**Non-goals**
- Создание сложной системы логирования ошибок на внешние сервера (например, Sentry) на данном этапе.
- Полный рефакторинг бизнес-логики (только оборачивание существующих вызовов).

## 2. Решения

### 2.1 Архитектура обработки ошибок

Предлагается внедрить трехуровневую систему:

1.  **Catch Layer (Перехват)**: Обертки вокруг API и функций БД, которые ловят `Throwable` и превращают их в типизированные `AppError`.
2.  **Translation Layer (Маппинг)**: Сервис `ErrorMapper`, который сопоставляет код ошибки (например, `PostgrestError 403`) с дружелюбным сообщением («У вас недостаточно прав для этого действия»).
3.  **Presentation Layer (Отображение)**:
    - **Toasts**: Для временных/некритичных ошибок (например, «Ошибка при сохранении, попробуйте еще раз»).
    - **Error Pages/Modals**: Для критических сбоев (например, «Сессия истекла, пожалуйста, войдите снова»).
    - **Inline Validation**: Для ошибок ввода (например, «Время должно быть кратно 5 минутам»).

### 2.2 Техническая реализация по категориям

#### 2.2.1 Сеть и Инфраструктура
- Создание `NetworkInterceptor`, который проверяет `window.navigator.onLine` перед запросом и обрабатывает тайм-ауты.
- Маппинг ошибок DNS/Connection $\rightarrow$ «Проблемы с подключением к серверу. Проверьте интернет».

#### 2.2.2 Аутентификация и Доступ
- Централизованный перехват ошибки `401 Unauthorized`.
- Автоматический редирект на `/login` с сохранением текущего URL для возврата после входа.
- Маппинг RLS ошибок $\rightarrow$ «Доступ ограничен».

#### 2.2.3 Синхронизация и Данные (Offline-first)
- Индикация статуса синхронизации в UI (статус-бар: «Облако синхронизировано» / «Ожидание сети...»).
- При возникновении конфликта версий при синхронизации $\rightarrow$ уведомление пользователя с предложением выбрать версию (или автоматический выбор по `updated_at`).

#### 2.2.4 UI и Логика
- Внедрение `React Error Boundary` вокруг основных модулей приложения для предотвращения полного краша страницы.
- Создание единого хука `useNotify()`, который предоставляет доступ к системе уведомлений из любой части приложения.

## 4. Риски и Ограничения

- **Производительность**: Излишнее оборачивание каждого мелкого вызова может незначительно увеличить нагрузку, что решается использованием легковесных функций-перехватчиков.
- **UX**: Слишком большое количество уведомлений может раздражать пользователя.
    - *Решение*: Группировка похожих ошибок и использование разных уровней важности (Info, Warning, Error).

## 5. План реализации (Roadmap)

1.  **Этап 1: Инфраструктура**. Создание классов ошибок, маппера и провайдера уведомлений.
2.  **Этап 2: API Wrapper**. Создание обертки для Supabase и интеграция её в приложение.
3.  **Этап 3: Auth & Network**. Реализация перехвата 401/403 ошибок и обработки отсутствия сети.
4.  **Этап 4: Sync & UI**. Добавление индикаторов синхронизации и Error Boundaries в интерфейс.
5.  **Этап 5: Валидация и Полировка**. Обертывание бизнес-логики и финальное тестирование всех сценариев из `project/error_scenarios.md`.
