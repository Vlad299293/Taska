## 1. Обзор

Цель — позволить пользователю начать пользоваться Taska (регистрация, вход, создание задач и блоков) даже при полном отсутствии интернет-соединения. Приложение должно работать в режиме «Локального профиля», который автоматически синхронизируется с облаком Supabase при восстановлении сети.

**Scope**
- **Локальный профиль**: Создание записи о пользователе в IndexedDB при «офлайн-регистрации».
- **Ограниченный режим**: Доступ к планировщику, созданию задач и таймеру без необходимости JWT-токена от Supabase.
- **Бесшовный переход**: Автоматический запрос на создание реального аккаунта в Supabase при появлении сети.
- **Синхронизация данных**: Перенос локально созданных задач в облако после успешной облачной регистрации.

**Non-goals**
- Полноценная совместная работа (Shared Workspaces) в офлайне (доступны только личные задачи).
- Валидация email в офлайн-режиме.

## 2. Решения

### 2.1 Логика «Офлайн-входа»

1.  **Перехват Auth-запроса**: Если пользователь нажимает «Войти» или «Зарегистрироваться», а сети нет:
    - Система проверяет наличие локального профиля в Dexie.
    - Если профиля нет $\rightarrow$ создается «Shadow Profile» (локальный UUID, временное имя).
    - Пользователь перенаправляется в приложение с пометкой `isOfflineMode: true`.
2.  **Локальная сессия**: Вместо JWT-токена Supabase, приложение использует локальный флаг сессии в `localStorage`.

### 2.2 Ограничение функционала

| Функционал | Offline Mode (Локальный) | Online Mode (Облачный) |
| :--- | :--- | :--- |
| **Создание задач** | ✅ Да (запись в Dexie) | ✅ Да (Dexie $\rightarrow$ Supabase) |
| **Запуск сессий** | ✅ Да (локальный таймер) | ✅ Да (синхронно с БД) |
| **Общие воркспейсы** | ❌ Нет (только личный) | ✅ Да |
| **Настройки профиля** | ⚠️ Только локально | ✅ Полный доступ |
| **Бэкап данных** | ❌ Нет | ✅ Да (автоматически) |

### 2.3 Процесс «Облачного повышения» (Promotion Flow)

Когда `window.navigator.onLine` становится `true`:
1.  **Уведомление**: Пользователю показывается Toast: «Сеть восстановлена! Хотите создать облачный аккаунт для сохранения данных?».
2.  **Регистрация**: При согласии приложение отправляет данные из «Shadow Profile» в Supabase Auth.
3.  **Миграция**:
    - Все локальные задачи с пометкой `synced: false` привязываются к новому `user_id` из Supabase.
    - Данные отправляются в облако пачками (batch upload).
    - Локальный статус обновляется на `synced: true`.

## 4. Риски и Безопасность

- **Дублирование аккаунтов**: Если пользователь создал локальный профиль, а затем зашел под уже существующим облачным аккаунтом.
    - *Решение*: Предложить слияние данных (Merge) или перезапись локальных данных облачными.
- **Потеря данных**: Если пользователь очистит кэш браузера до синхронизации с облаком.
    - *Решение*: Предупреждение в UI о том, что данные хранятся только локально.

## 5. План реализации (Roadmap)

1.  **Этап 1: Локальный профиль**. Настройка Dexie для хранения профиля и базовых данных пользователя.
2.  **Этап 2: Офлайн-Auth**. Изменение страниц входа/регистрации для поддержки режима «Shadow Profile».
3.  **Этап 3: Ограниченный режим**. Адаптация UI (скрытие функций совместной работы при `isOfflineMode`).
4.  **Этап 4: Синхронизатор**. Реализация процесса миграции данных из локального профиля в облачный при появлении сети.
5.  **Этап 5: Тестирование**. Проверка сценария: Регистрация (офлайн) $\rightarrow$ Работа с задачами $\rightarrow$ Включение сети $\rightarrow$ Синхронизация $\rightarrow$ Проверка в панели Supabase.
