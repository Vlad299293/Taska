## 1. Обзор

Полный отказ от централизованной облачной базы данных (Supabase) в пользу локального хранения на устройстве пользователя. Приложение переходит из модели Client-Server в модель **Standalone Desktop App**. 

**Цель**: Обеспечить максимальную скорость работы, 100% автономность и полную приватность данных.

**Scope**
- **Хранилище**: Замена `Dexie (IndexedDB)` и `Supabase` на `SQLite` через `tauri-plugin-sql`.
- **Авторизация**: Переход на локальную аутентификацию (хранение профиля в SQLite).
- **Данные**: Перенос всех схем таблиц (Tasks, Sessions, Blocks, Workspaces) в локальный файл БД.
- **Совместная работа**: Реализация модели «Хост $\rightarrow$ Гость» через экспорт/импорт зашифрованных данных или P2P соединение.

## 2. Техническая реализация

### 2.1 Слой данных (SQLite)
База данных будет храниться в системной папке приложения (`AppData` на Windows).

**Основные таблицы:**
- `local_profiles`: (id, email, password_hash, display_name, created_at)
- `workspaces`: (id, name, owner_id, is_host, invite_code)
- `tasks`: (id, workspace_id, title, description, status, priority, due_date, created_at, updated_at)
- `sessions`: (id, task_id, workspace_id, start_time, end_time, duration)
- `session_blocks`: (id, session_id, task_id, position, kind, planned_min, started_at, ended_at)

### 2.2 Новая модель авторизации
Больше нет запросов к `supabase.auth`.
1. **Первый запуск**: Пользователь создает локальный аккаунт $\rightarrow$ запись в таблицу `local_profiles`.
2. **Повторный вход**: Проверка пароля (хеш) в локальной БД $\rightarrow$ установка активного `userId` в состоянии приложения.
3. **Режим гостя**: Возможность использовать приложение без аккаунта (создание временного профиля).

### 2.3 Механика «Хост $\rightarrow$ Гость»
Так как центрального сервера нет, синхронизация данных между пользователями реализуется следующим образом:

1. **Создание приглашения**: Хост генерирует «Ключ доступа» (JSON-файл или зашифрованная строка), содержащий метаданные воркспейса и публичный ключ.
2. **Подключение гостя**: Гость импортирует этот ключ.
3. **Обмен данными**: 
   - **Вариант А (Static)**: Передача снимка (snapshot) базы данных.
   - **Вариант Б (Dynamic)**: Использование Tauri-команд для создания простого TCP-сервера/клиента внутри локальной сети для синхронизации задач в реальном времени.

## 4. План реализации (Roadmap)

1.  **Этап 1: Интеграция SQLite**. Установка `tauri-plugin-sql`, настройка инициализации БД при старте приложения.
2.  **Этап 2: Миграция Схемы**. Создание всех необходимых таблиц в SQLite (tasks, sessions, profiles).
3.  **Этап 3: Локальный Auth**. Реализация регистрации и входа через SQLite. Удаление всех упоминаний Supabase из UI.
4.  **Этап 4: Переписывание бизнес-логики**. Замена всех API-запросов к облаку на локальные SQL-запросы.
5.  **Этап 5: Система приглашений**. Реализация механизма передачи данных между Хостом и Гостем.
6.  **Этап 6: Очистка**. Полное удаление зависимостей `@supabase/supabase-js` из проекта.

## 5. Риски

- **Потеря данных**: Если пользователь удалит папку приложения, данные пропадут. 
  - *Решение*: Добавление функции «Резервное копирование (Экспорт БД в файл)».
- **Сложность P2P**: Реализация синхронизации в реальном времени между двумя ПК без сервера сложнее, чем с сервером.
  - *Решение*: Начать с простой модели импорта/экспорта данных.
