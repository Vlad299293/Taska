## 1. Обзор

Цель — превратить текущее веб-приложение Taska в полноценное десктопное приложение, которое обеспечивает базовую работоспособность без доступа к интернету (офлайн-режим), но синхронизирует данные с облаком (Supabase) при наличии сети, особенно для поддержки совместной работы над общими задачами в будущем.

**Scope**
- **Оболочка**: Перевод веб-приложения в десктопный формат (Electron или Tauri).
- **Офлайн-режим**: Локальное хранилище для кэширования данных сессий и задач.
- **Синхронизация**: Механизм обновления локальных данных из облака и отправки локальных изменений в облако.
- **Дистрибуция**: Создание установщика (installer) для ОС.

**Non-goals**
- Реализация полноценного P2P (Peer-to-Peer) обмена данными.
- Сложная система разрешения конфликтов (на первом этапе — стратегия "последний записавший побеждает" или ручной выбор).
- Создание нативного UI (используем существующий веб-интерфейс).

## 2. Решения

### 2.1 Технологический стек
Для реализации десктопного приложения и офлайн-режима предлагается следующий стек:

- **Framework**: **Tauri** (рекомендуется над Electron из-за меньшего размера бинарника и лучшей производительности, так как бэкенд на Rust позволяет эффективно работать с локальной БД).
- **Local Storage**: **IndexedDB** (через библиотеку `Dexie.js`) или **SQLite** (через Tauri API). 
    - *Выбор*: **Dexie.js (IndexedDB)** — проще в интеграции с существующим Next.js/React фронтендом и не требует сложной настройки БД на стороне пользователя.
- **Sync Layer**: Кастомный слой синхронизации между Dexie.js и Supabase.
- **Packaging**: Tauri Bundler (создает `.exe`, `.dmg`, `.deb` установщики).

### 2.2 Стратегия Офлайн-работы

1. **Кэширование**: При запуске или при наличии сети приложение скачивает актуальные данные пользователя (задачи, активные сессии) в IndexedDB.
2. **Локальные правки**: Все действия пользователя (создание задачи, завершение блока) записываются в локальную БД с пометкой `synced: false`.
3. **Фоновая синхронизация**:
    - При появлении сети приложение ищет все записи с `synced: false` и отправляет их в Supabase.
    - После успешного ответа от сервера запись помечается как `synced: true`.

### 2.3 Синхронное использование и Общие задачи
Для поддержки будущих «общих задач» (shared tasks):
- **Timestamp-based Sync**: Каждая запись в БД получает поле `updated_at`. При синхронизации приложение запрашивает только записи, измененные после последнего успешного sync-timestamp.
- **Realtime**: Использование `Supabase Realtime` (уже частично внедрено в проекте) для мгновенного обновления интерфейса, когда другой пользователь меняет задачу в общем воркспейсе.

### 2.4 Процесс установки (Installer)
- **Tauri Build**: Сборка проекта в один исполняемый файл.
- **Installer**: Генерация `.msi` (Windows) или `.dmg` (macOS) установщика.
- **Автообновления**: Интеграция `Tauri Updater` для автоматического обновления приложения без необходимости повторного скачивания установщика.

## 4. Безопасность и Риски

- **Данные на диске**: Локальная БД IndexedDB не зашифрована по умолчанию. Для чувствительных данных потребуется рассмотрение шифрования (если это станет критическим требованием).
- **Конфликты синхронизации**: Если один и тот же блок был изменен в офлайне на двух устройствах, возникнет конфликт.
    - *Решение*: На первом этапе — побеждает более поздний `updated_at`.
- **Доступ к сети**: Приложение должно корректно обрабатывать переходы Online $\to$ Offline $\to$ Online без потери данных.

## 5. План реализации (Roadmap)

1. **Этап 1: Оболочка**. Интеграция Tauri, запуск текущего сайта в окне приложения, создание первого установщика.
2. **Этап 2: Локальное хранилище**. Внедрение Dexie.js, создание зеркала таблиц `tasks` и `sessions` локально.
3. **Этап 3: Синхронизация**. Реализация базового флоу: `Cloud $\rightarrow$ Local` (загрузка) и `Local $\rightarrow$ Cloud` (отправка изменений).
4. **Этап 4: Совместная работа**. Настройка Realtime-обновлений для общих воркспейсов.
5. **Этап 5: Дистрибуция**. Финальная сборка установщика с иконками и оптимизацией размера.
